# 恒川支付运营 · 支付对账与差错追踪

> 从业务挖掘到可运行 MVP 的完整交付：**渠道账单与交易流水之间的差异定位辅助**。
> 只读方案 —— 不退款、不调账、不发起资金划转。

---

## 一句话说明

每日 80 万笔交易、对账员 5 小时查异常、未解释差异 180 笔/日。本交付把"哪笔对不上"推进到"为什么对不上"，
并把结论做到**可复核、可追溯、可验收**三条线上：

- **可复核** —— 每条差异可回指原记录与待确认字段；
- **可追溯** —— 哈希链审计，能从流水归集重建到复核；
- **可验收** —— 指标双口径，分母与排除规则写死并同时披露。

## 核心结论（三条）

**一、问题不在算法，在数据口径。** 交易号、商户订单号、渠道号关系不完整、时区不一致，
  导致逐笔匹配从第一步就失败。行业数据佐证：参考字段一致时匹配率 91%，不一致时降到 76%，
  相差 15 个百分点，超过交易量、账户类型、行业等因素的影响。所以先做质量校验，再谈匹配优化。

**二、99.9% 的口径必须写死。** 行业公开的自动匹配率天花板是 89%–96%，"99.9% 全部自动匹配"不存在。
  99.9% 只能按"已给出结论的样本里错误不超过 1 条"理解，且分母与排除规则必须与指标同时披露——
  否则通过调整排除规则就能把数字做漂亮，这正是 f40 明令禁止的"用猜测匹配掩盖差异"。

**三、系统只到"建议"为止。** 行业产品的核心卖点是自动冲正、自动调账，而本项目明确只读。
  这不是能力缺失，而是风险边界：资金调整必须双人复核，失败一旦发生在损害之后便不可撤销。

## 运行 MVP

零第三方依赖，Python 3.9+：

```bash
cd docs/05-mvp
python run.py            # 跑一次离线回放，生成复核台与明细
python run.py --serve    # 本地复核台 http://127.0.0.1:8787
python -m unittest discover -s tests -v
```

产物在 `docs/05-mvp/sample/out/`：

| 文件 | 内容 |
|---|---|
| `差异定位复核台.html` | 单文件交互式复核台（指标 / 差异下钻 / 工单 / 审计） |
| `差异清单_diff_list.csv` | 168 笔差异，含证据引用与建议 |
| `转人工工单_tickets.csv` | 44 单，含触发条件 / 岗位池 / SLA |
| `审计留痕_audit.jsonl` | 哈希链，可逐条复算 |
| `指标快照_metrics.json` | 口径与指标，随报告冻结 |

一次回放的结果：渠道结算 1093 行 → 参与自动匹配 1053 笔 → 差异 168 笔（转人工 44 单）→
可查原因覆盖率 100%、未解释差异 0 笔、审计链校验通过。

> 样本为**合成数据**，缺陷按访谈描述构造，因此 100% 的准确率是设计使然，**不构成 99.9% 达标的证据**。
> 真实结论必须以真实账单回放复测。

## 数据与合规声明

- 全部业务数据为**合成样本**，不含任何真实商户、交易或个人信息。
- 依据为合成场景访谈提炼的 36 项事实（f00–f55），属**待验证假设**，非已确认需求。
- 方案为只读旁路，不写回任何业务系统，不具备退款/调账/划转能力（代码层有测试守护）。
- 行业数据均为公开资料，统计口径互不相同，仅用于判断区间与量级。
