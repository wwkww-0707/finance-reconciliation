## 一、设计目标与边界

### 1.1 三个设计目标

1. **把"哪笔对不上"变成"为什么对不上"**——每条差异必须带原因码、证据引用、规则版本，缺一项即判为未解释。
2. **让结论可信到可以签字**——匹配结论可回指原记录，人工可复核、可退回、可留痕。
3. **把不可逆风险挡在系统之外**——系统只出建议，任何资金动作回到人工流程。

### 1.2 明确不做什么

| 不做 | 原因 | 依据 |
|---|---|---|
| 自动退款、自动调账、自动平账 | 不可逆，且与双人复核红线冲突 | f40 / f05 |
| 自动生成调整分录 | 同上 | f42 |
| 实时对账 | 数据源每天两次只读快照，不具备实时条件 | f34 |
| 对外自动回复/承诺赔偿 | 争议受理与赔付口径未定 | f54 |
| 多渠道路由与规则编排 | 首期只做单渠道，避免范围蔓延 | f02 / f05 |
| 用模型替代规则做定性 | 差异定性涉及责任，必须人签 | f22 |

### 1.3 与现有系统的关系

方案是**只读旁路**，不替换支付网关、渠道账单库、财务总账中的任何一个（f30）。数据单向流入，不写回：

```
支付网关 ─┐
渠道账单库 ─┼─→ [只读快照] ─→ 本方案（纯计算） ─→ 复核台/工单/审计
财务总账 ─┘                        │
                                   └─×─→ 任何业务系统（禁止写回）
```

## 二、总体架构

### 2.1 五层 + 两个贯穿

| 层 | 职责 | 关键设计 | 失败兜底 |
|---|---|---|---|
| L1 材料层 | 归集四类材料，登记版本与快照时间 | 版本号 + 快照时间戳；超一个周期标"待刷新" | 用上一份只读快照，界面显式提示 |
| L2 校验层 | 字段级质量校验（Q1–Q7） | 命中的记录进修复队列，**不进入自动匹配样本** | 修复后重新入队 |
| L3 匹配层 | 分层匹配，输出置信度 | 五层由严到宽；低置信不输出结论 | 转人工候选 |
| L4 定位层 | 归因到 10 类原因码，组装证据链 | 有限枚举 + 证据引用 + 规则版本 | 无法归因 → 单边账 + 转人工 |
| L5 协同层 | 工单分派、复核、签核 | 四类强制转人工；接手人与确认时间必填 | 超时升级 |
| 贯穿 A | 审计留痕 | 哈希链，六要素齐全 | 链路校验失败即告警 |
| 贯穿 B | 指标与口径 | 双口径（验收/全量），排除项同步披露 | 口径快照随报告冻结 |

### 2.2 部署形态

| 阶段 | 形态 | 说明 |
|---|---|---|
| 回放验证 | 单机脚本 + 静态复核台 | 无外部依赖，历史数据只读加载，跑完即出报告 |
| 并行试点 | 内网服务（单实例） | 只读数据库账号 + 定时快照，页面内网访问 |
| 推广（暂缓） | 多渠道实例化 | 需先完成口径与权限评审 |

### 2.3 不可变边界

系统内有三处硬边界，不允许通过配置绕过：

1. **只读边界**：数据访问层只提供 `read`，不存在写接口（f32）。
2. **结论边界**：匹配引擎的输出是「建议」，字段名为 `suggestion`，不是 `decision`（f05）。
3. **签核边界**：涉及资金动作的工单必须 `double_check=true` 才可关闭（f40）。

## 四、数据模型

### 4.1 核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| 对账批次 `batch` | batch_id、channel、settle_date、snapshot_version、rule_version、created_at | 一次回放一个批次，版本号是审计锚点 |
| 渠道结算行 `channel_row` | row_id、settle_date、settle_batch、merchant_id、merchant_order_no、channel_order_no、gross_cents、fee_cents、net_cents、txn_type、channel_time | 对账的基本单元，金额以「分」为整数存储 |
| 内部流水 `ledger` | txn_id、biz_no、merchant_id、merchant_order_no、channel_order_no、gross_cents、fee_cents、fee_rule_version、pay_time、txn_type | 支付侧事实 |
| 退款事件 `refund` | refund_id、orig_merchant_order_no、orig_channel_order_no、refund_cents、refund_time | 跨日退款归属的唯一依据 |
| 差异 `diff` | biz_no、reason_code、root_cause、evidence_refs、rule_version、snapshot_version、suggestion、disposition、confidence | 审计与工单的源头 |
| 工单 `ticket` | ticket_id、biz_no、trigger_code、pool、assignee、created_at、sla_deadline、confirm_time、double_check | 人工兜底的载体 |
| 审计事件 `audit_event` | seq、type、biz_no、stage、doc_version、fact_refs、suggestion、manual_change、signer、prev_hash、hash | 哈希链节点 |

### 4.2 三条建模约定

1. **金额一律用整数分**。浮点会在合并入账的和值校验里产生 1 分误差，进而把正常交易判成差异。
2. **时间一律带时区**，内部统一 `+08:00`。渠道给的 UTC 时间在入库时转换为内部口径，同时保留原始偏移用于时区冲突判定。
3. **业务编号贯穿始终**。`biz_no` 是差异、工单、审计三张表的连接键，也是对外解释的检索键（f54）。

## 五、匹配策略

### 5.1 分层与置信度

| 层 | 规则 | 置信度 | 结论 |
|---|---|---|---|
| L1 | 商户订单号 + 金额 + 交易类型精确 | 0.995 | 直接匹配 |
| L2 | 渠道订单号 + 金额 | 0.985 | 直接匹配 |
| AGG | 同一商户当日全部流水，金额与手续费双校验和值 | 0.970 | 匹配 + 需拆分核销（D02） |
| REF | 退款事件反查原支付单 | 0.980 | 匹配 + 归属判定（D01） |
| L3 | 金额 + ±36 小时时间窗，且窗口内唯一候选 | 0.900 | 匹配但标注低证据强度 |
| L3-AMBIG | 同额候选 ≥2 | — | **不输出结论**，转人工（D10） |

### 5.2 合并入账拆分规则

渠道按商户按日汇总入账，因此拆分组 = 「同一商户 + 同一结算日 + 未占用流水」，校验条件是**金额和值与手续费和值同时相等**。

不做子集穷举的原因：在 1000+ 条候选里穷举组合，几乎必然能凑出一组"和值相等但成员错误"的组合。这种伪匹配会把真实差异抹平，正是 f40 禁止的"用猜测匹配掩盖差异"。

### 5.3 跨日退款归属规则

渠道按支付日归属、内部按退款发生日记账，于是 D 日结算出现负金额冲销行而内部当日无对应流水。判定路径：

1. 结算行为 `REFUND` 类型 → 用 `merchant_order_no` 反查退款事件表；
2. 退款时间晚于结算日 → 判 D01（跨日退款未归属），证据 = 退款事件 ID + 原支付单号；
3. 退款时间与结算日同日 → 判正常（归属期间一致）。

若退款事件表本身过期（D09），则 D01 的判定依据不足，必须降级为转人工——这也解释了为什么"退款事件"是四类必备材料之一（f21）。

### 5.4 金额一致不等于无差异

样本中有 8 笔交易金额完全一致、手续费相差 1 分。只比较交易金额会把这类差异当作正常放过，形成"匹配上了但说不清为什么"的典型来源。因此校验必须同时覆盖 `gross_cents` 与 `fee_cents`。

## 六、差异原因码与证据链

### 6.1 十类原因码

| 码 | 名称 | 根因 | 处置 |
|---|---|---|---|
| D01 | 跨日退款未归属 | 退款在结算日次日，渠道按支付日冲销 | 需人工确认 |
| D02 | 手续费合并入账 | 多笔合并为一条结算行，单笔无法对号 | 需人工确认 |
| D03 | 重复订单 | 通知超时，商户重试导致内部重复建单 | **转人工 E1** |
| D04 | 时区偏移冲突 | 渠道 UTC 与内部 +08:00 相差 8 小时 | 修复队列 |
| D05 | 主编号缺失 | 缺商户订单号，无法建主键关系 | 修复队列 |
| D06 | 规则版本冲突 | 两版费率生效期重叠 | **转人工 E3** |
| D07 | 金额/手续费差异 | 未登记通道费或分位取整不一致 | 需人工确认 |
| D08 | 单边账 | 仅一侧存在，另一侧无对应流水 | 需人工确认 |
| D09 | 快照过期 | 数据源超一个更新周期 | **转人工 E4** |
| D10 | 低置信候选 | 同额多候选，缺独立核验依据 | **转人工 E2** |

### 6.2 可查原因必填字段

`biz_no`、`reason_code`、`root_cause`、`evidence_refs`（≥1 条）、`rule_version`、`snapshot_version`、`suggestion`。

缺任一字段 → `explained=false` → 计入"未解释差异"。这一条是 99.9% 验收的实际抓手：只要未解释差异不为 0，准确率就没有意义。

## 七、人工兜底与权限

### 7.1 四类触发（f44，缺一不可）

| 触发 | 条件 | 必须标注 | 双人复核 |
|---|---|---|---|
| E1 重复订单 | 同一商户订单号多笔支付成功 | 触发原因、接手人、确认时间 | 是 |
| E2 资料缺依据 | 证据不足或置信度低于阈值 | 同上 | 否 |
| E3 版本冲突 | 两版规则均可解释且生效期重叠 | 同上 + 两个版本号 | 是 |
| E4 系统不可用 | 数据源缺失或快照过期 | 同上 + 快照时间 | 否 |

### 7.2 角色权限矩阵

| 操作 | 渠道运营员 | 对账会计 | 支付数据工程师 | 资金风险经理 | 商户服务主管 |
|---|---|---|---|---|---|
| 查看差异清单 | 仅本渠道 | 全部 | 全部（脱敏） | 全部 | 关联本商户 |
| 查看四类原始材料 | 只读（授权范围） | 只读 | 只读 | 只读 | 否 |
| 确认接手工单 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 修改建议结论 | ❌ | ✅（留改动理由） | ❌ | ✅ | ❌ |
| 签核资金动作 | ❌ | ❌ | ❌ | ✅（双人） | ❌ |
| 导出审计链 | ❌ | ✅ | ✅ | ✅ | ❌ |
| 删除/归档评价记录 | ❌ | ❌ | ❌ | ✅（需复核） | ❌ |

### 7.3 SLA 与升级

- 工单创建即写 `sla_deadline = created_at + 240 分钟`；
- 超时未接手 → 自动升级至支付运营经理（f25）；
- 确认时间以**人工首次响应**为准，不以系统接收为准（待书面确认，见 REQ 待验证项 3）。

## 八、审计与留存

### 8.1 六要素（f45）

每次建议与改动必须记录：业务编号、资料版本、事实引用、建议结果、人工改动、签核人。不记录账号口令与不必要个人信息。

### 8.2 哈希链

```python
rec = {seq, ts, type, biz_no, stage, doc_version, fact_refs,
       suggestion, manual_change, signer, prev_hash}
rec["hash"] = sha256(prev_hash + canonical_json(rec))
```

- `prev_hash` 指向上一条的 `hash`，首条指向 64 个 0；
- 任意中段修改都会让后续链条校验失败，`verify()` 返回断点位置；
- 审计时可一键证明"这条链没被动过"，而不是"我们相信它没被动过"。

### 8.3 留存（f43）

| 对象 | 期限 | 到期处理 |
|---|---|---|
| 原始材料快照 | 按场景授权范围 | 不因评价记录到期被连带清除 |
| 差异与工单 | 与原始材料同期 | 归档 |
| 本轮评价记录 | 90 天 | 资金风险经理复核后删除或归档 |
| 审计链 | 与差异同期 | 只增不改 |

## 九、指标与口径

| 指标 | 口径 | 基线 | 目标 |
|---|---|---|---|
| 未解释差异 | 每日结算，含两侧 | 180 笔/日 | 40 笔/日 |
| 发现到定位 | 六节点计时，不含人工调整与复核 | 6 小时 | 1 小时 |
| 匹配准确率（验收口径） | 正确结论 ÷ 进入自动匹配笔数 | — | ≥ 99.9% |
| 匹配准确率（全量口径） | 正确结论 ÷ 全部结算行，转人工计未命中 | — | 仅披露，不设目标 |
| 可查原因覆盖率 | 7 项字段齐全的差异 ÷ 差异总数 | — | 100% |
| 未解释差异笔数 | 缺任一必填字段 | — | 0 |
| 转人工率 | 工单数 ÷ 结算行数 | — | 对标行业例外率 4%–11% |

**排除规则**：修复队列（主编号缺失/时区冲突）、低置信候选（D10）、快照过期数据（D09）不计入准确率分母，但必须与指标同时披露，不得单独报准确率。

## 十、实施计划

| 阶段 | 周期 | 交付 | 里程碑判定 |
|---|---|---|---|
| P0 口径对齐 | 第 1 周 | 指标定义草案、权限矩阵、转人工分派机制 | 傅景签核口径 |
| P1 质控回放 | 第 2–3 周 | 字段级校验清单、主编号缺失率/时区冲突率 | 得到匹配率上限结论 |
| P2 匹配与定位 | 第 3–6 周 | 五层匹配、10 类原因码、证据链 | 单渠道回放可解释率 100% |

> P0 不通过则 P1 不启动。这不是流程形式主义：口径未定就开发，最后一定是"数字好看但没人认"。

## 十二、验收清单（Definition of Done）

**功能**
