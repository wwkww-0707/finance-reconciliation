# 对账差异定位台 · 最小 MVP

> 恒川支付运营 · 支付对账与差错追踪 · 渠道账单与交易流水差异定位
> 只读辅助工具，**不产生任何资金动作**（不退款、不调账、不发起划转）

## 1. 这个 MVP 解决哪一段

发现报告把首期切入点定在「**先做单渠道离线差异定位辅助，以数据质量校验和人工兜底为前置条件**」（REQ-1 / REQ-2）。这个 MVP 就落在这句话上，只做三件事：

1. **匹配前先验数据**——主编号、时区、时间、金额、规则版本六类字段级校验，脏数据进修复队列，不污染匹配结论；
2. **匹配后必须给原因**——每一条差异都带原因码、根因、证据引用、规则版本、建议动作，缺一项就计入「未解释差异」；
3. **结论出去之前先过兜底**——重复订单、资料缺依据、版本冲突、系统不可用四类情形强制转人工，标注触发原因、接手人、确认时间。

它**不是**一个自动对账系统。它替代的是"人翻流水找差异"里最耗时的定位环节，把"这 180 笔为什么对不上"从 5 小时压到分钟级，处置动作仍然回到人。

## 2. 快速开始

零第三方依赖，Python 3.9+ 即可运行。

```bash
cd docs/05-mvp

# 跑一次离线回放，生成报告与明细
python run.py

# 重新生成合成样本（固定随机种子，结果可复现）
python run.py --regen

# 启动本地复核台（在线重跑、人工接手写审计）
python run.py --serve          # http://127.0.0.1:8787

# 单元测试
python -m unittest discover -s tests -v
```

产物：

| 文件 | 说明 |
|---|---|
| `sample/out/差异定位复核台.html` | 单文件复核台，双击即可打开，数据已内联 |
| `sample/out/差异清单_diff_list.csv` | 全量差异清单（168 笔），含证据引用与建议 |
| `sample/out/转人工工单_tickets.csv` | 兜底工单，含触发条件、岗位池、SLA、双人复核标记 |
| `sample/out/审计留痕_audit.jsonl` | 哈希链审计日志，可逐条复算 |

## 3. 一次回放的结果

样本：单渠道 `CH-WEIXIN-A`、结算日 `2026-10-27`、内部流水 1138 笔、渠道结算 1093 行（含 36 笔退款冲销行、12 条合并入账行）。

| 指标 | 结果 | 口径 |
|---|---|---|
| 参与自动匹配 | 1053 笔 | 全量 1093 − 修复队列 33 − 低置信 7 |
| 匹配准确率（验收口径） | **100.00%**（1053/1053） | 自动匹配且原因码正确 ÷ 分母 |
| 匹配准确率（全量口径） | 100.00% | 转人工 40 笔计入未命中 |
| 可查原因覆盖率 | **100.0%** | 必填字段齐全 ÷ 差异总数 |
| 未解释差异 | **0 笔** | 缺任一必填字段的差异 |
| 差异总数 | 168 笔 | 转人工 44 单 |

差异分布：

| 原因码 | 名称 | 笔数 | 处置 |
|---|---|---|---|
| D01 | 跨日退款未归属 | 36 | 需人工确认 |
| D03 | 重复订单（通知超时重试） | 24 | 转人工（E1） |
| D07 | 金额/手续费差异 | 24 | 需人工确认 |
| D08 | 单边账 | 19 | 需人工确认 |
| D04 | 时区偏移冲突 | 18 | 修复队列 |
| D05 | 主编号缺失 | 15 | 修复队列 |
| D06 | 手续费规则版本冲突 | 12 | 转人工（E3） |
| D02 | 手续费合并入账 | 12 | 需人工确认 |
| D10 | 低置信候选 | 7 | 转人工（E2） |
| D09 | 快照过期 | 1 | 转人工（E4） |

> **关于 100% 这个数**：合成样本里的缺陷都是按规则构造的，能被规则识别是设计使然，**不构成 99.9% 达标的证据**。真实回放必然出现规则未覆盖的差异，所以验收必须以真实账单回放复测，本 Demo 只证明"口径可定义、结果可复现、差异可解释"。

## 5. 关键设计取舍

**为什么匹配前要卡质控？**
交易号、商户订单号、渠道号关系不完整、时区不一致（f31）时，匹配算法再强也只能给出似是而非的结论。先把这类记录挡在自动推荐样本之外（f33），才能保证剩下的结论可信。代价是分母变小、覆盖率下降——这个代价是明示的，不是藏起来的。

**为什么不用"最像的那一笔"兜底？**
差额对不上就报差异，不做强行匹配。一旦用猜测填补，差异被抹平了，账却不平（f40：不能用猜测匹配掩盖差异）。

**为什么金额一致还要比手续费？**
样本里 8 笔交易金额一致、手续费差 1 分。只比金额会把这类差异当"正常"放过——这正是"匹配上了但说不清为什么"的典型来源。

**为什么要哈希链？**
单条日志可以被删改而不留痕。每条记录哈希指向前一条，中段篡改会让后续链条校验失败，审计时能证明"这条链没被动过"（f45）。

## 6. 已知盲区与下一步

| 盲区 | 影响 | 下一步 |
|---|---|---|
| 未接入真实账单与网关接口 | 结论仅代表合成样本 | 取一个渠道近两周真实资料跑回放（REQ-1 下一步） |
| L3 金额+时间窗层仍会自动出结论 | 同额多笔时有误判可能 | 降级为"候选提示"，不输出匹配结论 |
| 服务侧解释工单未建模 | 反馈闭环缺基线（REQ-5） | 采集两周工单量与首次响应时长后再纳入 |
| 六节点人工段（N4-N6）未计时 | 无法拆解 6h→1h 的改善来源 | 在试点中按节点打点（REQ-6） |
| 无真实权限体系 | 岗位最小化视图未验证 | 接入现有账号体系，按岗位授权 |
